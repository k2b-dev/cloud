### A fresh browser's one-time shader compile landed in the first WebKit test

- **What happened:** `directory access 390 light: exact share, error recovery and revoke` in `packages/accounts/src/directory-shares.browser.test.ts` timed out after 5 s in WebKit on #2133, which does not touch Accounts. The other five variants took about 2 s (#2149). In every WebKit shard of that run, the first test was slower than the next one.
- **Root cause:** Each CI job starts a new Playwright container. WebKit in that image draws through Mesa's software renderer. A new container has no shader cache, so the first frames compile 70–100 shaders. That one-time cost of 3–4 s fell inside the first test that drew anything. The fixture uses no `@k2b/ssr` navigation, so the view-transition fix from #2126 did not apply. In a newly created container the first test failed every time. In a restarted container, or with a seeded shader cache, it passed.
- **Error class:** Cold-start costs land in the budget of the first test.
- **Guard:** `bun run test --browser` first runs `packages/ui/test/browser-warm-up.ts`. It drives real `@k2b/ui` components (panel dialog, combobox list, menu, light and dark) and logs how long it took, inside the shard's `--max-minutes`. Test budgets are unchanged. With a fresh container, the first test took 2.3–3.3 s after the warm-up, against 6.1–7.2 s without it (measured with a 30 s budget). `scripts/run-tests.test.ts` checks that the warm-up script exists and is not collected as a test file.
