### Menus and tabs in @k2b/ui replaced their rows when the host rebuilt equal items

- **What happened:** After #2154 and #2164, an audit of the other interactive lists in `@k2b/ui` found the same class in `Dropdown` (and so in `ContextMenu` and `GestureMenu`, which render `DropdownItems`) and in `Tabs`. A host that rebuilt its menu items or tab options while a button was down replaced the row, and the click did nothing.
- **Root cause:** These rows rendered with `<For>` over objects. `Tabs` builds new option objects whenever a tab's props change. Hosts pass menu items as JSX literals that are rebuilt with every signal they read.
- **Error class:** A list keyed by object identity replaces interactive elements when the host rebuilds equal data.
- **Guard:** A shared internal `KeyedFor` keeps a row's element for the same object (also when its getters change) and for a new object with the same identity (menu label, tab value). It reads identities untracked: the table menu's `items` getter builds new objects on every read, so a tracked label getter re-read the list and replaced its rows, which `text-editor-table-menu.behavior.test.tsx` caught in CI. `pressAcrossRebuild()` in `packages/ui/test/browser.ts` is the shared test step for this class, and `rebuilt-rows.browser.test.ts` uses it for menus and tabs; it failed for all three cases before the change. The focus convention in `docs-site/src/ui/context/focus.md` now names clicks too. A check rule was not added: the code alone cannot tell an interactive list from a static one. Not affected: `FileTree`, which reuses its nodes, and the editor's slash menu, which picks on `mousedown`. Not changed: the prompt search list, whose items have no stable identity in the public type.
