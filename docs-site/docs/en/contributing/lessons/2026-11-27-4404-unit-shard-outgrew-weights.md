### Cap a unit suite below the shard target and name the suites that drift

- **What happened:** The unit shard 6/13 stopped at its 20-minute budget during `@k2b/ui rest`, so a merge group failed although no test failed (#4386). In green runs the same shard already took up to 18.8 min.
- **Root cause:** `scripts/test-weights.json` still weighted `@k2b/ui rest` at 693 s. New v2 browser tests had grown it to 1000 s, more than the 15-minute target for one suite alone. `@k2b/ui layout-content` (859 s) and `@k2b/cloud-app-notebooks` (921 s) were as large.
- **Error class:** The measured time of a suite drifts away from its committed weight until one suite fills a shard by itself. This is the fourth lesson of this class, after [a larger suite keeps its old shard weight](2026-10-26-pr-1903-a-larger-suite-keeps-its-old-shard-weight.md), [shard estimates drifted](2026-10-27-ci-shard-runtime-drift.md) and [a unit shard reached its time limit](2026-11-01-unit-shards-at-their-time-limit.md). A static test reads only the committed table, so it cannot see stale weights.
- **Guard:** `scripts/run-tests.test.ts` caps every unit suite at nine tenths of the target, so one suite can never fill a shard alone. At run time, a shard prints a warning that names each suite that took more than 1.2 times its weight; refresh the table with `bun scripts/test-weights.ts --run <ids> --mode unit`, or split the suite.
