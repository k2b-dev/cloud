### A WebKit Tab test scrolled the day view now and then

- **What happened:** "Tab from the header enters the day on screen without changing the scroll position" timed out in WebKit on a README-only pull request. Locally it failed about one run in eight: the focus reached the right day, but the days scrolled up by half a view.
- **Root cause:** WebKit puts an element that `focus()` gives the focus on screen in its next rendering update, and then reveals whatever has the focus by that time. The test focused the view switcher with `locator.focus()` and pressed Tab within the same frame. The Tab moved the focus into the days, and the reveal that was still pending then landed on the day's heading. The scroll padding that keeps entries clear of the sticky heading makes that heading count as covered, so WebKit centered it. A person cannot press Tab that soon after the previous focus, so the product was not affected.
- **Error class:** Browser tests that act sooner than a person can, so the engine's deferred work from one step lands on the next.
- **Guard:** The test now gives the switcher the focus with `preventScroll`, which leaves no reveal pending; it passed 25 of 25 WebKit runs. Tests that check the scroll position after a key focus the starting element the same way. No repository check, because a rule cannot tell which `focus()` calls precede a scroll assertion.
