### A hydration repair waited a full round of folder checks per body

- **What happened:** On a production account with 354 folders, bodies that an operator retried with `mail repair hydration` waited about 957 s for the provider lease.
- **Root cause:** The repair reset the failed bodies and queued only the mailbox's hydration job. That job asks for the lease with `background` priority and no head start. Folder checks ask with `sync` priority and a 60-second head start, and one round over 354 folders takes longer than 60 s. So the job waited behind about every folder check of the account. The per-message hydration job, which ranks with commands, already existed but was not used.
- **Error class:** Work that a person explicitly asked for runs at background priority behind a queue that grows with the size of the account.
- **Guard:** The repair queues per-message jobs for the newest pending bodies, at most 12. That is the budget a person has per minute and mailbox for opening messages. More would hold back the mailbox's later commands, because they share the command class. The mailbox's own job still loads the rest. The bodies are chosen from the pending bodies, not from the rows this run resets, so a repair that runs again queues them again. `provider-lease-fairness.integration.test.ts` runs a one-message repair and lets the job it queued ask for the lease behind one holder and 354 waiting folder checks. The job must get the next turn: the folder check first in line is refused. The test fails with the old repair both at the queued job and at the turn order. A second test checks the bound of 12 and the repeated run.
