### A container added to an event place silently removed its readability check

- **What happened:** After Files entries gained the container `filesv2.folder` (#3487), the platform no longer generated `filesv2.entry.readable`. Code could no longer be activated on Files upload events; activation failed closed with "This event place has no supported read-access check" (#3539).
- **Root cause:** The derived event-place reader skipped contained Types, and every readability check of a contained Type required an expected container. Code binds an event registration to its place only, so Core had no container to send. Event delivery already checked the same place through its ordinary reader without a container (`packages/cloud/src/services/app-events/deliver.ts`).
- **Error class:** A shared Type change (adding a container) withdrew a capability another feature depends on, and only a pinned test noticed.
- **Guard:** `tests/capability-presentation.test.ts` requires the derived `filesv2.entry.readable` without a container input. `packages/cloud/src/capabilities/resource-readers.test.ts` proves that other callers of a contained Type still fail without its container and find no derived reader with one. The `event-place-exception` repository check (`scripts/checks/event-place-exception.ts`) allows the `eventPlace` option only in its defining module and `packages/core/src/code/event-access.ts`. `packages/cloud/src/code/foreign-events.test.ts` requires the readability contract for every real event place again. `packages/cloud/src/_internal/event-place-reader.test.ts` covers the account that may read the place, the one that may not, a failing reader, and a check that names a container.
