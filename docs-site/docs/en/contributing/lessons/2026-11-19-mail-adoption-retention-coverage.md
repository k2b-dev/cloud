### Every draft replay consumer must honor committed pruning coverage

- **What happened:** A Mail editor could reconnect from its covered snapshot but fail to save its next edit with a retention-gap error. Older 0.78 snapshot recovery could also quarantine covered drafts; restarting the process does not repair that stored flag.
- **Root cause:** The snapshot loader already included the committed idle proof, but `refreshDraftAdoption` still replayed from `doc_cursor`. Snapshot saving calls that human-authorship check before advancing the SQL projection, so the stale cursor rejected an otherwise complete save. Current idle coverage alone cannot prove that an older incomplete-history recovery lost no input.
- **Error class:** Inconsistent replay coverage between consumers of a pruned shared log.
- **Guard:** `draft-document-socket.integration.test.ts` opens a real Mail room, snapshots another draft and prunes the global prefix, then rejoins with the old cursor. It requires unchanged revision and complete history after rejoin, followed by a successful edit, exactly one new revision and retained human adoption. It fails with the previous adoption reader. Existing tests retain valid input and the original snapshot for genuinely uncovered or malformed history. The adoption query reads coverage in its existing row-locked statement; no SQL statements are added. The operations guide requires independent evidence before restoring incomplete history and preserves the original when that evidence is absent.
