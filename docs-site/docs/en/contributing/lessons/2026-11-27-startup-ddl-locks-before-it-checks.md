### A start took the table lock of IF NOT EXISTS DDL and queued every writer behind a dump

- **What happened:** A start during `pg_dump`, next to another replica's index build, or behind a long transaction stopped at the first `ALTER TABLE … ADD COLUMN IF NOT EXISTS`. Until the other session ended, every reader and writer of the table waited behind the migration (#4492).
- **Root cause:** Postgres takes the table lock before it checks `IF NOT EXISTS`. Measured on Postgres 17 with nothing to change: every `ALTER TABLE` form takes ACCESS EXCLUSIVE (`ADD COLUMN IF NOT EXISTS`, `DROP COLUMN IF EXISTS`, `DROP CONSTRAINT IF EXISTS`, `SET NOT NULL`, `SET DEFAULT`). `CREATE INDEX IF NOT EXISTS` takes SHARE and `CREATE TRIGGER` takes SHARE ROW EXCLUSIVE. `DO` blocks that check the catalog first, `CREATE TABLE IF NOT EXISTS`, and `DROP INDEX IF EXISTS` on a missing index take no table lock. Most startup migrations ran without `lock_timeout`, so the waiting statement had no bound.
- **Error class:** Idempotent DDL that is safe to repeat but still takes a table lock on every start.
- **Guard:** `@k2b/cloud/services/migration-ddl` (`addColumns`, `createIndexes`, `replaceTrigger`, `withTableLock`) checks the catalog first. It locks only for a real change and waits at most 2 s per attempt, in up to 8 attempts. The rule `startup-ddl-locks` keeps a per-file baseline of `ADD COLUMN IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS` in TypeScript and SQL sources, which may only shrink. The same class through row locks, a rewrite of every `ai.conversations` row on every start (#4515), now runs only when the search columns, function or trigger changed. `migration-ddl.integration.test.ts` holds a dump lock and an index-build lock on `ai.conversations` and on Core's busiest tables, then requires `migrateCloudAi()` and Core's migrations to finish and a concurrent INSERT to pass; a third session keeps one conversation row locked.
