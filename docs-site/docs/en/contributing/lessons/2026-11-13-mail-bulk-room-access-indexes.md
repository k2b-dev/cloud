### Index both branches of a bulk-delete trigger lookup

- **What happened:** Deleting 10,000 message links through Mail's thread-rebuild repair repeated a lookup over all open shared drafts for each deleted link. Measurements did not demonstrate an end-to-end speedup from indexing that lookup.
- **Root cause:** The row trigger searched drafts by source or derived message ID. The existing source index covered one branch, but the mailbox-leading derived index could not cover the other. PostgreSQL scanned the document-coverage index and filtered its shared drafts for every deleted link.
- **Error class:** A row trigger repeats a lookup whose indexes do not match its full predicate.
- **Guard:** `room-access-bulk.integration.test.ts` deletes 10,000 links through `executeOperatorAction`, pins nine client statements with `meterSql()`, and requires indexed source and derived lookups with `EXPLAIN (ANALYZE, BUFFERS)`. The plan assertion covers trigger work that the client SQL meter cannot count. The existing source index and one new partial derived index let the lookup probe message IDs instead of filtering all open shared drafts per deleted row. Migration tests verify the derived partial index, upgrade creation outside a transaction, preservation of the existing source index, and idempotent reruns. Room-access tests verify coalesced mailbox hints for source and derived drafts, including cascades and unrelated private or closed drafts.
