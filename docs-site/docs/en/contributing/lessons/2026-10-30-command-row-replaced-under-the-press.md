### A command row replaced under the press swallowed the click

- **What happened:** `catalog and resource recovery in real panel at 1440px` in `packages/chat/src/frontend/ChatPanel.browser.test.ts` failed twice in WebKit (#2140). After a click on "Notes", the command menu was closed, the composer still said `/notes`, and the resource dialog never opened. People could hit the same thing: a click on a command that does nothing.
- **Root cause:** `ChatComposer` rendered command rows with `<For>` over the command objects. The Assistant rebuilds those objects whenever its catalog, state, or draft changes, for example while a recovered catalog settles. A row whose object changed was replaced by a new button. When that happened between the press and the release, the browser sent the click to a common ancestor, and no command ran. The `k2b-anchored-popover` in the report was the model chooser's hidden surface; its press handler acts only while it is open.
- **Error class:** A list keyed by object identity replaces interactive elements when the host rebuilds equal data.
- **Guard:** Rows are keyed by `chatCommandKey` and read their current command, so the button under the pointer survives a rebuild. `packages/ui/src/chat/chat-composer.browser.test.ts` rebuilds the commands between `mouse.down()` and `mouse.up()` and expects the command to run, in WebKit and Chromium; it failed in both engines before the fix. The ChatPanel failure report now lists the last presses and clicks per frame, and whether each dialog is visible.
