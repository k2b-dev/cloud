### Browser fixtures did not answer the shell's own capability catalog read

- **What happened:** Unrelated pull requests failed in browser tests (#1855: Spaces `item-list.browser.test.ts` collected `404 …/api/capabilities/v1/catalog?limit=25` as an error; #1843: an Accounts test counted that read as its first write; #2075). Locally the tests passed, because the read happened only sometimes before the test ended.
- **Root cause:** `packages/cloud/src/browser/files.tsx` starts the file-provider discovery when the page is idle, through `requestIdleCallback` or, in WebKit, a 1 s timer. The discovery reads `GET /api/capabilities/v1/catalog?limit=25`. Every page that imports `@k2b/cloud/browser/files` makes this read. Fixtures written before the read existed served only their own endpoints and answered it with 404. Some fixtures answered it by hand.
- **Error class:** A shared module makes a request of its own on page load, and test fixtures that serve only their own endpoints leave it unanswered depending on timing.
- **Guard:** Every page from `launchBrowser()` in `packages/ui/test/browser.ts` answers this read in the page with an empty catalog, before any request, so no fixture sees it. A test file that serves the catalog, counts its reads, or fails it on purpose launches with `serveShellCatalog: true`. `packages/ui/test/browser.browser.test.ts` checks in Chromium and WebKit that the default sends no request, that other reads and writes still reach the fixture, and that the option passes the served catalog through. A context route was rejected, because Playwright then disables the HTTP cache of the whole context.
