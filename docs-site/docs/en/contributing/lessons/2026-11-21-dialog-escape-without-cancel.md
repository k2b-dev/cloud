### Escape closed a dialog, and the dialog opened itself again

- **What happened:** In WebKit the app launcher sometimes stayed open after Escape (#3916): `AppAccessEditor.browser.test.ts` waited 5 s for `dialog[open]` to disappear, and it never did. The launcher is a plain `dialogCore` dialog without a guard.
- **Root cause:** The dialog core reopened its frame on every native `close` it had not asked for, because a guarded or must-answer level has to survive a forced close after repeated Escape. Browsers with close watchers also close a modal dialog on Escape without a `cancel` event, for example without a recent user activation. That close never reached the core's dismissal, so the `close` handler opened the dialog again; the browser test reproduces this path in Chromium. Which of the two ways WebKit took in the failing run, a close without `cancel` or an Escape that reached neither, is not visible in its log; the fix covers both: an Escape that did not reach `cancel` had no other way to dismiss the dialog.
- **Error class:** A handler for a forced browser close treats every close it did not cause as unwanted, while the browser also uses that path for the person's own close request.
- **Guard:** `packages/ui/src/feedback/dialog-escape.browser.test.ts` closes dialogs natively without a `cancel` event and presses Escape right as a dialog opens: a plain dialog stays closed and resolves as dismissed; a `cancelBehavior: "ignore"` dialog stays open; a guarded dialog stays open and asks its guard. The core also dismisses a modal level after an Escape that nothing prevented and no popover took, when the browser did not route it to `cancel`.
