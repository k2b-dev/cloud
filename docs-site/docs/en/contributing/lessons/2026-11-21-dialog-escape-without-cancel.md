### Escape closed a hint the dialog's own opening had shown

- **What happened:** In WebKit the app launcher sometimes stayed open after Escape (#3916): `AppAccessEditor.browser.test.ts` waited 5 s for `dialog[open]` to disappear. A diagnostic in the test then showed, in CI, the "Customize app bar" tooltip open at the moment of the Escape.
- **Root cause:** `showModal()` focuses the dialog's first focusable control; in WebKit that focus counts as visible, so the control's hint (delay 0) opened. The dialog core moved focus to the level's own first target only a frame later. An Escape in between closed the hint, as hints must on Escape, and the dialog stayed. A person in Safari saw a stray hint and lost the first Escape. Two more ways to keep a dialog after Escape surfaced on the way: the core reopened its frame on every native `close` it had not caused, also when a browser closed the frame without a `cancel` event; and an Escape that never reached `cancel` had no other way to dismiss.
- **Error class:** An overlay's first focus is applied a frame late, while the browser's own pick already triggers focus-dependent behavior (hints, key handling) on another control.
- **Guard:** `dialog-escape.browser.test.ts` covers a native close without `cancel` (plain, must-answer, guarded), Escape without a user activation, and Escape at the moment of opening; `dialog-dismiss.behavior.test.ts` pins that the first focus is set before any frame. The launcher test now waits for focus in the launcher and fails with the markup of any popover that would take the key.
