### Startup waited for concurrent index builds

- **What happened:** The AI migration awaited `CREATE INDEX CONCURRENTLY` for `ai.inference_calls_all_turn` while Core started. A concurrent build waits for every older snapshot, so one long transaction, such as a nightly dump, could hold Core's start. A restart during the build could turn into a restart loop. The workflow retention indexes and Core's send log indexes each had their own copy of the build logic, and only Core's started without being awaited. Moving a build into the background brings a second risk: the build holds its table for as long as it runs, and a later `ALTER TABLE … ADD COLUMN IF NOT EXISTS` or `CREATE INDEX IF NOT EXISTS` of the same table takes its lock before it checks the catalog. Another replica's start then waits behind the build, and every write of the table waits behind that start.
- **Root cause:** Each place that needed an index next to live writes wrote its own build. Nothing stopped a migration from awaiting one, or from taking a strong lock on a table that a build holds.
- **Error class:** A migration awaits work, or a lock, that can wait without bound on other sessions, so a running app's start depends on transactions it does not own.
- **Guard:** Concurrent index statements go through `packages/cloud/src/services/concurrent-index.ts`, and the rule `concurrent-index-builds` fails on one anywhere else. A migration starts the build with `buildConcurrentIndexesInBackground` and never awaits it. The table's own DDL runs through `addMissingColumns` and `createIndexIfMissing`, which take a lock only when the catalog lacks the column or index. `concurrent-index.integration.test.ts` holds an old snapshot and checks that `migrateCloudAi` still returns, and it holds the lock of a running build and checks that the AI migration neither waits nor blocks writes. The class is not closed everywhere yet: Mail still awaits its startup builds (#4491), and other migrations still take strong locks unconditionally (#4492). A UNIQUE index that a transaction relies on is not a background index: it is built before its first use, with a `lock_timeout` and a retry.
