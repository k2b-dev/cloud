### A browser test read the page while a form post still navigated it

- **What happened:** In WebKit, `session-origin.browser.test.ts` failed with "Execution context was destroyed, most likely because of a navigation" (#4468, seen on #4404). Each round of the test clicked a form's Submit, waited for the POST's response and went on to the next page. The form post navigates the page to its answer, and the test did not wait for that. The next round's `page.goto` and its probe (`packages/ui/test/browser.ts`) then read a page whose document was still being replaced.
- **Root cause:** A response arriving is not the navigation ending. A native form post loads its answer as a new document after the response; WebKit commits it later than Chromium, so the next read met it in the middle.
- **Error class:** A test waits for a network signal (`waitForResponse`) when the next step depends on the page's state (the navigation that response causes).
- **Guard:** Every form post in `packages/cloud/src/server/middleware/session-origin.browser.test.ts` now waits in the same `Promise.all` for its response and for the page to leave the form's address and load the answer (`page.waitForURL((url) => url.href !== form)`), before the next read. All assertions stay: a foreign post never writes. The file ran 10 times in WebKit, all green. No repository rule: a POST response next to a click looks the same in code for a form post, which navigates, and for a `fetch`, which does not (98 `waitForResponse` calls today), so a rule would mostly flag correct tests.
