### The pairing dialog test compared a box from before the layout settled

- **What happened:** In one WebKit run (`ipad-834 dark`), the test "a further pairing waits in the place of the code" read the dialog at top 449 for the code and at top 395 for the wait, with the same height of 296 px. It looked like the dialog moved up by 54 px when it started to wait.
- **Root cause:** The run's base still had the footer hold from #3929, which #4027 later removed. When the code arrived, the dialog grew by 108 px from its center. In a later frame, a resize observer lifted the dialog by half of the growth (`--k2b-dialog-lift: 54px`). In WebKit, the centered frame stayed for 59 to 171 ms before the lift. The test measured the code right after `locator.waitFor()` for the code text, in that gap. It measured the wait after the lift. The dialog did not move between the code and the wait.
- **Error class:** A test compares boxes of two states, but it reads the first box right after a wait for content. A locator `waitFor` finds the content in its first frame. Layout that reacts to the content, such as a resize observer, fonts or images, can change the box later. The `settle-reads` check counts locator `waitFor` as a settle, so it does not report this read.
- **Guard:** `measure()` in `packages/core/src/pages/app-approval/approval-dialogs.browser.test.ts` awaits `settled(page)` itself, so the file cannot compare a box from before the layout settled. The pairing case also records the dialog's box on every frame and resize, from the code to the wait. It requires one box, so it also finds a move that comes back. A probe that moved the dialog by 20 px for two frames passed the old check, but this guard found it. A stricter `settle-reads` check that does not count locator `waitFor` as a settle would report 865 more reads in 106 files, so this lesson does not change the check.
