### Finish draft fixture work before replacing its dependencies

- **What happened:** An attachment revision in a Mail session test could appear to conflict with newer typing. Repeated runs also exposed shared draft state and WebSocket traffic in later fixtures.
- **Root cause:** Three quiet five-millisecond request intervals do not prove that cleanup finished. A controlled SHA-256 promise demonstrates that a close-time PUT can outlive that window and change the next fixture's stored text. Shared initialization can outlive disposal and spy restoration. An offline shared close can reconnect after one second and send a snapshot POST; broad POST counters then count another session's snapshot as a lease acquisition. Controlled regressions reproduce both mechanisms. The original CI request URLs were not recorded, so attribution of that particular failure remains unverified.
- **Error class:** Asynchronous test work escapes its owning fixture's lifecycle.
- **Guard:** Controlled hash, initialization and reconnect cases cover the lifecycle boundaries. Lock fixtures with a held lease wait for the final release; shared fixtures join initialization, saves and offline storage before restoring dependencies. Request accounting retains fixture ownership across root work, public session calls and socket callbacks; it reports requests from those owners after completion or unexpected requests after session disposal. Intentional close-time PUT, lease DELETE and shared snapshot requests remain allowed until fixture completion. The original reload and attachment scenarios and assertions remain unchanged.
