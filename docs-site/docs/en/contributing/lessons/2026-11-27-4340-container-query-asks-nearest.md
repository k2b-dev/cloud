### A main column beside its context column could not scroll: a container query asked the column, not the split's place

- **What happened:** In #4340, a main column with 1000 rows beside its context column (`side={{ from: 1600 }}` at 1700 × 700) did not scroll at all. Its `.k2-scroll` computed `overflow-y: visible` inside a pane and a split that both clip, so the list window fell back to the page.
- **Root cause:** The split's wrap rule styled `.k2-split > .k2-pane > .k2-scroll` inside `@container k2-host (width < room)`. A container query resolves against the subject's nearest ancestor of that name. For the scroller, that is its own pane, which #4340 also made a `k2-host`. A column beside its context is always narrower than the room, so the "given way" rule always held. The fixtures had 14 rows, which fit without scrolling.
- **Error class:** A container query whose name more than one ancestor carries, used for an element deeper than the element the author had in mind.
- **Guard:** Each contextual split is now a container under a name only it carries (`k2-split-<id>`), and every rule for what stands inside it asks that name. Only the split's own rule asks its place (`k2-host`). `packages/ui/src/v2/context-column.browser.test.ts` checks a main column of 200 rows beside its context at 1920 px: its scroller is `overflow-y: auto`, taller than its box, and scrolls. It also checks that both columns' scrollers are `auto` in every side-by-side case. The test failed first on c2caec02bf.
