### A prompt that loaded its code first opened with the context of the moment the code arrived

- **What happened:** A form prompt, a typed confirmation, a phone prompt sheet or a phone date sheet asked for before its code had loaded could open in the default palette inside an AI-coloured area. It could also open over a page that `@k2b/ssr/nav` had navigated to in the meantime, and return focus to whatever was focused when the code arrived (#3782).
- **Root cause:** `dialogCore.open` reads the palette scope, the island-disposal count and the opener when it is called. Several callers called it only after awaiting their chunk: `prompts.form`, `confirmPrompt` with a `confirmationPhrase`, the phone sheet in `openPrompt`, and the date sheets of `DatePicker` and `PeriodPicker`. The "form unavailable" message after a failed load did the same. So all three values came from a later moment. WebKit does not focus a clicked button, so focus is often somewhere else when the code arrives.
- **Error class:** A function that reads ambient state (focus, palette, page generation) is called after an `await`, so it reads the state of a later moment than the call that asked for it.
- **Guard:** `captureDialogOpen()` in `packages/ui/src/feedback/dialog-core.ts` reads the context synchronously at the call and opens through `dialogCore.open` with it later; a navigation in between resolves `undefined` without opening. Every dialog in `@k2b/ui` whose code loads first uses it: the prompts, the error message after a failed load, `openPromptSheet` and `openDateSheet`, which require the captured `open`. `packages/ui/test/prompt-call-context.behavior.test.ts` and `packages/ui/test/date-sheet-call-context.behavior.test.tsx` move the focus and dispose islands while the chunks are pending, and fail on the old code. No repository check, because a rule cannot tell which reads after an `await` depend on ambient state.
