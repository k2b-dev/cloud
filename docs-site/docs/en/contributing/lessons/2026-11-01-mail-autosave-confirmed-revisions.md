### Draft autosave must confirm uncertain writes before newer input

- **What happened:** A committed draft save whose response was lost could make the next edit report a revision conflict. Reopening the draft could ignore newer local input because its journal carried an older revision.
- **Root cause:** Revision checks ran before exact-content confirmation, no-op writes advanced revisions, and local recovery treated an old base revision as old text. Shared snapshot completion also checked input typed after the save began. A granted lease also exposed the draft before asynchronous journal recovery finished. Local cleanup could run before accepting a committed revision, and explicit recovery could replace a peer version without retaining it.
- **Error class:** Uncertain write replay and stale-base recovery.
- **Guard:** Mail draft integration tests cover no-op and lost-response replay; draft-session behavior tests cover serialized coalescing, stale journals, safe metadata reconciliation, local storage quota/cleanup failures, and reverting after an uncertain save. Delayed native-hash tests keep initialization and persistence blocked until journal recovery finishes, preserve sign-in and closed-draft actions during recovery, and reject a conflict discovered while reacquiring a lease. A failed local backup must not prevent server persistence or roll back a confirmed client revision. Compose browser tests cover 60 seconds of typing with header edits, timeout retries, and two-tab recovery without overwriting either version, and reply recovery within an assigned conversation, including offline journals without a server recovery copy. Server restoration uses the same mutation queue as autosave and retains the replaced content and attachment snapshot in the same transaction. Shared-document tests require coverage of the submitted snapshot and stable revisions for idle snapshots without draft input.
