### An opened message waited minutes for its body behind folder checks

- **What happened:** In production, an opened message showed **Der Nachrichteninhalt wird noch synchronisiert** for about four minutes. The reader gave no deadline, and **Nachricht aktualisieren** only reloaded the reader. It never asked for the body.
- **Root cause:** The body's arrival hydration waited in the account's provider-lease queue with `sync` priority, the same class as every folder check of the mailbox. The measured lease waits were 74 s on one mailbox and 471 s on a mailbox with 354 folders. Raising all arrival hydration to `command` is not the fix: the 2026-11-01 lesson shows that body backlogs then starve folder continuations. Only the body that a person waits for needed the `command` class. `enqueueMessageHydration` already gave it that class through a per-message job, but the reader never used it.
- **Error class:** A wait that a person sees runs at background priority, and the screen gives no honest state once that wait outlasts its expected time.
- **Guard:** `provider-lease-fairness.integration.test.ts` holds the lease with one folder check while 20 more wait. A body request made through the reader's service must get the next turn: each of the 20 folder checks asks for the free lease first and is refused. This assertion fails when the per-message job uses `sync` priority. `message-body-request.integration.test.ts` covers the access check, one job per message and window, a wait that continues after reload, the reset of a failed body, and a limit of 12 prioritized bodies per minute, person and mailbox. The reader behavior tests require one request per open and a new request from **Nachricht aktualisieren**. They also cover the 30-second deadline and the failed state with a retry. `MailMessageCard.browser.test.ts` requires that loading, waiting, and failed states take the same height at 1280, 390 and 320 px, in English and German.
