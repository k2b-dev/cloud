### A hydration failure named no column, and only one fixture covered broken text

- **What happened:** Message `5RwrDw` in a production mailbox failed hydration with `ERR_POSTGRES_SERVER_ERROR` on every attempt. The log showed only that code, so nobody could tell which part, column or value Postgres refused. The fix for NUL bytes was tested with one combined fixture.
- **Root cause:** The hydration failure log lines wrote only Mail's error code. Postgres reports the SQLSTATE, the refused parameter, and often the table, column and constraint, and none of that was kept. Fixtures shaped like the production message show where NUL fails without normalization. NUL in the 8bit inline text fails at the body's search text (`unnamed portal parameter $4`). NUL in a quoted, RFC 2231 or encoded-word attachment name fails at the part's file name (`$8`). Invalid UTF-8 alone does not fail, because the decoder replaces it with U+FFFD.
- **Error class:** Untrusted mail bytes are written to Postgres text without normalization, and the failure log keeps none of what the database said about it.
- **Guard:** `databaseErrorFacts` names the SQLSTATE, the parameter number, the table, the column and the constraint, never a value or the rest of Postgres' context. Every hydration failure log line uses it: a single message, a message in a source batch, a mailbox batch, and exhausted retries. `message-hydration-text.integration.test.ts` has one fixture per place: NUL and invalid UTF-8 in the 8bit inline text, in the base64 text attachment, in an RFC 2231, encoded-word or quoted file name, and in headers. Each requires the message to load, all stored text to be free of NUL and well-formed, and the attachment to keep its original bytes. The NUL fixtures fail without the normalization from #2576.
