### A renderer parity test spends its deadline starting another runtime

- **What happened:** The KaTeX on-demand behavior test exceeded its unchanged five-second deadline in the merge queue. Its server comparison then failed between tests with empty expected output and two lines of rendered browser HTML.
- **Root cause:** The test synchronously started a fresh Bun process and imported the Markdown renderer inside its deadline. The failed run logged `killed 1 dangling process` at five seconds, before the child wrote its reference output. The test compared stdout without checking whether the process completed. The test DOM does not implement `document.compatMode`, which also caused an unrelated KaTeX warning; Cloud uses `renderToString`, which that warning does not disable.
- **Error class:** A rendering behavior test includes unrelated process startup in its deadline and treats an interrupted child's output as a rendering result.
- **Guard:** `katex-parity.test.ts` and `katex-on-demand.behavior.test.ts` independently compare the real server and browser renderers against one checked-in HTML reference, including inline and block math. The browser test retains its initial source, reactive completion, and subsequent-render assertions. Convention: use this shared-reference pattern for renderer parity across runtime conditions instead of starting a comparison process inside a behavior test. Timeouts and budgets stay unchanged.
