### A browser action started before WebKit rendered its first frames

- **What happened:** The Assistant context suite, newly included in the WebKit gate, timed out on its first Working files click. The same failure reproduced in a fresh Playwright container with two CPUs.
- **Root cause:** Suspected: the suite began pointer actionability checks before WebKit delivered its first rendered frames. Document load does not guarantee rendering. In the reproduced failure, Playwright's frame-based stability check remained pending without reporting an unstable or hidden element; the page then answered script evaluation in 40ms, and the button had visible geometry and no animations. The exact reason WebKit withheld frames was not measured. The launcher migration in `4198049da` exposed the failure; later unmodified cold runs also passed, so a green run alone does not prove the diagnosis. No sidebar product defect was demonstrated.
- **Error class:** Document readiness mistaken for rendering readiness before a browser interaction.
- **Guard:** The suite explicitly observes two frames in the page's main world with `waitForFunction`, checks the sidebar's 320px column, and clicks Working files. All three steps share one deadline of 3000ms after `goto`; the whole test retains its 20-second budget. `settle-reads` requires synchronization before the geometry assertion; the click itself is not statically guarded. An unbounded `settled()` call and separate frame/click budgets were rejected because they would extend the original first-action budget. Existing collector assertions continue to report real page errors. Whether main-world frame observation prevents the intermittent utility-world stall remains unproven.
