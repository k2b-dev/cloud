### Mail boundaries disclosed whether unreadable resources exist

- **What happened:** Mail capabilities and REST routes answered differently for existing unreadable IDs and unknown IDs: 403 versus 404, or different 404 messages. The mailbox SSR page also redirected an outsider for an unknown folder or saved view in an existing mailbox, while an unknown mailbox returned 404. These differences disclosed existence; they did not grant access to content.
- **Root cause:** Public ID resolution, workspace selection, validation, or write authorization ran before the relevant read visibility check. Mailbox read access alone did not establish visibility of conversations, drafts, messages, or scheduled deliveries under an assigned-only grant. A separate Cloud administrator shortcut also bypassed the credential scope cap already enforced by lifecycle authorization.
- **Error class:** Existence oracles include differences in status, redirects, and complete error messages. Two 404 responses can still disclose existence. Visibility checks must precede validation and operation-specific authorization when the response could depend on a hidden resource.
- **Guard:** Capabilities use `resolveMailboxScope` before mailbox-owned lookups, and `resolveConversationScope` checks assigned conversation visibility, including the conversation selected by `draft.create`; message references check assigned visibility before triage, comments, or draft creation. Direct readers and both phases of `delivery.cancel` normalize hidden resources to the same resource-specific not-found error as unknown IDs; cancellation checks visibility before write permission. `resolveMailboxParam` uses scope-capped lifecycle authorization for administrator exceptions. `resolveMailboxResourceParam` checks assigned conversation, message, draft, and scheduled-delivery visibility before REST validators or write checks. Delivery visibility is independent of scheduling or failure state, preserving operation-specific errors for visible deliveries. Body/query relations, command message IDs, and derived draft seeds reuse the same visibility check, so changing the input shape cannot bypass it. Reminder target routes normalize hidden and unknown reminder errors. The mailbox page checks read access before `resolveWorkspaceRequest` can redirect. Keep release retains its independent authority check. Operations that refuse known and unknown IDs identically retain that refusal, and callers with visibility retain precise permission and validation errors.
- **Regression coverage:** `capability-mailbox-boundary.integration.test.ts`, `mailbox-route-boundary.integration.test.ts`, and `assigned-resource-boundary.integration.test.ts` compare complete capability errors and REST responses across outsider, assigned-read, and assigned-write identities. The SSR guards compare status and redirect behavior; `mailbox-page.render.test.ts` asserts that unreadable mailboxes never reach workspace selection or loading, while readable requests retain search parsing, overload handling, and precise errors. Positive controls cover readable resources, assigned conversations, validation errors, write refusals, scope-capped administration, and deleted-mailbox lifecycle. These guards do not assert equal response timing.
