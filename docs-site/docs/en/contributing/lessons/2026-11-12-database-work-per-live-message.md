### Shared drafts ran about 100 SQL statements per keystroke

- **What happened:** Shared Mail drafts saved every Yjs update synchronously. Each keystroke checked access, locked the draft row (`FOR UPDATE`), rebuilt the document, wrote the projection and the revisions, and ran an SQL fence for each delivery. With 200 drafts, p95 reached 14 seconds. An audit with a statement meter then found that Notebooks also ran 8 statements per edit: two snapshot reads, three access queries, and a row-locked transaction for each delivery and receiving socket (#3232). The platform's `shared-text` `accept()` also reads the store and replays the log for every update (#3231).
- **Root cause:** Mail built its own socket path beside the platform's live and shared-text mechanisms. It checked and persisted inside the per-message handler. Nothing measured the cost of one message, so no test failed as the count grew.
- **Error class:** Database work per live message: SQL, a row lock, or a stored-document load per message, keystroke, event, or delivery, where an access check at join, access-change events, fan-out over NATS, and lazy persistence would do. It often comes with a parallel mechanism that an application builds beside the platform's.
- **Guard:** Convention DATA-13 in [Live updates](/en/docs/automation/live-updates#keep-the-database-out-of-the-live-path), the `cloud-dev` skill, and `AGENTS.md`. `meterSql()` in `scripts/fixtures/sql-meter.ts` counts statements in tests. `packages/cloud/src/server/middleware/request-budget.integration.test.ts` pins 2 statements per signed-in request. `packages/notebooks/src/ws-edit-budget.integration.test.ts` pins today's 8 per edit, which #3231 and #3232 lower to 0.
