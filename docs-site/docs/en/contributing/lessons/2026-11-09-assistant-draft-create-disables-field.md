### The Assistant's first draft save locked the field and closed the "/" list

- **What happened:** In WebKit, `Assistant full-view Command Escape restores editing during create at 1440px` in `packages/chat/src/frontend/ChatPanel.browser.test.ts` (#2095) waited 8 s for the opening's create and failed after 11.6 s. Nothing in the run pointed at Assistant code.
- **Root cause:** A new chat's draft saves itself 2 s after the last edit and creates the chat first. While any create ran, the composer was disabled. A disabled field loses focus, so the "/" list closed, and keys typed meanwhile went nowhere; after the create, focus stayed on the page body. A slow runner took longer than 2 s from "Plan /" to the click on "Create task", so the click found no list. Locally, a 2.5 s pause before that click gave the same error and the same 11.4 s; a person who pauses in the list sees the list close.
- **Error class:** A background save that disables the control the person is using. Also, a test that races a real-time delay of the product instead of holding the request that delay starts.
- **Guard:** The field stays editable while the draft's own save creates the chat. A send or an app command started meanwhile waits for that create and continues in the new chat, because `createConversation` joins it instead of answering `null`. `Assistant keeps the field usable while the draft's own save creates the chat` holds that create, for a command and for a send, and fails on the old code. The Command Escape test holds every create, whether the draft's save or the opening starts it, so its result does not depend on how fast the runner is.
