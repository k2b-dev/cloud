### Successful background checks accumulated a trace for every run

- **What happened:** Background trace storage grew to tens of gigabytes while successful runs repeatedly inserted and updated spans.
- **Root cause:** The Sync observer persisted lifecycle starts before knowing whether a run had any diagnostic value.
- **Error class:** Per-execution diagnostics turn routine background activity into unbounded storage and write load.
- **Guard:** `problem-runs.integration.test.ts` runs 1,000 successful jobs and uses SQL triggers to assert zero span writes and one minute upsert; it also checks failures, retries, slow runs and size retention. `run-rollups.test.ts` checks exact count, sum, maximum and minute identity without timing assertions. `trace-retention.integration.test.ts` keeps older failures, recovered retries, slow runs, and minute counts before newer routine successes; 10,001 randomized-key spans and 10,001 events require multiple physical block ranges with heartbeats and cancellable progress. EXPLAIN checks a TID range scan without sorting or a primary-key scan, and a one-byte excess still triggers deletion. Invalid byte settings preserve age cleanup. `scheduler.test.ts` checks default and configured retention budgets, forwarding the worker heartbeat and abort signal. Jobs omits sampled error rates, and 1,024 missing settlements cannot prevent a fresh slow-start observation.
