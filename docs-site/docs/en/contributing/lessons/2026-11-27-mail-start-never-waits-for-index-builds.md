### Mail's start waited for its index builds and looped while another build ran

- **What happened:** Mail's migration awaited `CREATE INDEX CONCURRENTLY` for the shared-draft access index, the F6 consolidation index and the unique reply-box index. One long transaction held the start, and while another backend built one of them the migration threw "retry startup when it completes", so every restart failed again. Each start also ran `ALTER TABLE … ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS` and `CREATE OR REPLACE TRIGGER` on `mail.drafts` and the other tables that background builds use. These statements take their table lock before they look, so a running build made them wait for the lock timeout and fail the start, and writes queued behind them meanwhile.
- **Root cause:** Startup treated the unique index as the guarantee of one open reply draft per conversation, so it waited for it. Only a conversation merge relied on the index; every other writer already took the reply-box lock. Idempotent DDL looked harmless because it changes nothing when the object exists.
- **Error class:** A migration awaits or locks against work it does not own: a concurrent index build, or the old snapshot it waits for.
- **Guard:** All Mail builds go through `@k2b/cloud/services/concurrent-index` under Mail's one-build-at-a-time lease and start after the migration (`buildMailIndexes`); the `concurrent-index-builds` rule no longer lists Mail. F6's upgrade start builds its indexes with plain builds while the earlier image is stopped, and commits the unique index with its `completed` marker. A merge takes both conversations' reply-box locks and checks itself, so a later missing unique index is only a missing backstop. On build tables, `migrate-catalog.ts` runs DDL only when the catalog lacks its object. `migrate-startup.integration.test.ts` holds an old snapshot, runs a foreign build, and holds the build lock on every table in `MAIL_CONCURRENT_INDEXES` while Mail migrates; `one-reply-draft.integration.test.ts` checks that a merge keeps one open reply draft per conversation before and after the unique index is valid.
