### New mail that IMAP IDLE reported waited behind every folder check

- **What happened:** In production, new mail took minutes to appear in Cloud, even though IMAP IDLE reported it at once. In ten minutes there were 14,211 busy lease attempts for 263 committed batches, and 50 to 95 folder jobs were always waiting. Earlier measurements showed lease waits of 74 s and 471 s.
- **Root cause:** A push from the listener became a folder sync with `sync` priority, the same class as every scheduled check of every other folder of the mailbox. The job did not carry its trigger, so the pushed Inbox lined up behind all the folder checks that were already waiting. The listener's own minute check and polling used the same trigger as a real push.
- **Error class:** A wait that a person sees runs at background priority. This is the same class as the 2026-11-04 lesson about opened message bodies, on a second path.
- **Guard:** `provider-lease-fairness.integration.test.ts` holds the lease with one folder check while 20 more wait. A pushed Inbox sync must get the next turn: each of the 20 checks asks for the free lease first and is refused, and the checks continue in order after the Inbox. A second test pushes during every Inbox batch. The Inbox then takes every other turn, and the folder checks get the rest. Command and other work already alternate on the lease, so no new limit is needed. `sync-recovery.integration.test.ts` uses `meterSql` to require that a pushed turn costs no statement beyond the first turn's folder read, and that a busy turn keeps the push. `imap-push-runtime.test.ts` requires that only a change the server announces counts as a push, also when it comes with a removal that needs reconciliation. The listener's own minute check, polling without IDLE, and an uncertain stream alone do not count.
