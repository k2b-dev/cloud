### A note linked from thousands of notes sent every backlink to its details

- **What happened:** Opening a note sent all of its backlinks to the page, and `GET /api/notebooks/:id/notes/:noteId/backlinks` returned all of them. A note linked from 1,000 notes put 1,000 rows into the details, about 15,500 DOM nodes with the note's other lists, and each render took 5–6 s. Outgoing links beside them were already capped at 100 (#4417).
- **Root cause:** `listBacklinks` had no limit, so every caller (the note's route state, the API, the CLI) read the whole set. The outgoing links got a limit when they were added; the backlinks, older, never did.
- **Error class:** A list read whose size is set by other people's data (here: how many notes link to one), with no page size from a contract, so one popular record makes every read of it grow.
- **Guard:** `listBacklinks` takes a required `limit` and reads one page and the total in one statement. `backlinks.integration.test.ts` links 1,000 notes to one note and pins one statement per page with `sql-meter`, the newest-first order, the total, access filtering and a page past the end. The note's route state reads the first page of 100 (`NOTE_LINKS_PAGE`, the API's `per_page` maximum; `route-state.test.ts`), the API pages with the platform's `PaginationQuerySchema`, and the details load further pages on demand by page number and the server's `has_next` (`detail-panel.browser.test.ts`, 250 backlinks, including one that moves between pages). Pages follow `updated_at`, so an edit while someone pages can repeat or skip a backlink until the list is read again; the details drop repeats by id. For this list that is accepted.
