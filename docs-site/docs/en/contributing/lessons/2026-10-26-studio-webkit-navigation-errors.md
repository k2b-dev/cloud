### Browser suites mistook navigation cancellations for page failures

- **What happened:** Studio management and editor tests failed in WebKit with an access-control message for the page's own capability catalog. Fixing only the management suite left the same failure in the editor and other browser tests.
- **Root cause:** The suites adopted the shared WebKit launcher in #935 but retained raw page-error listeners. WebKit reports a same-origin load refused while a test-started document navigation is pending as a page error, even when the application handles the failed request. A collector already existed, but no repository check required callers to use it.
- **Error class:** Browser navigation diagnostic mistaken for an unhandled application failure; a local fix left other callers of the same contract exposed.
- **Guard:** Browser tests across all packages use `pageErrors(page)` and retain their error assertions. The `browser-page-errors` check rejects hand-rolled listeners for `pageerror` and context `weberror` in tests, shared browser suites, fixtures, and harnesses, with exact exceptions for two diagnostic probes. Its regression tests cover other packages, helper-based fixtures, listener spellings, and the narrow exceptions. Separate console assertions remain for hydration, expected warnings, and telemetry. `packages/ui/test/browser.browser.test.ts` reproduces the navigation refusal and verifies that the collector still reports ordinary uncaught errors, real cross-origin failures, unhandled rejections, and refusals during page-started navigation.
