### The detail float test timed the closing slide with the wall clock

- **What happened:** `detail-float.browser.test.ts` failed in WebKit on a loaded runner because the closing slide seemed to take 307 ms, which is more than the 300 ms bound ([#1622](https://github.com/k2b-dev/cloud/issues/1622)). The panel declares a 140 ms slide. Any pull request whose WebKit shard ran this file could fail.
- **Root cause:** The test measured the time between the click and the first frame that showed `display: none` with `performance.now()`. When frames arrived late, that time grew, but the slide itself did not change. The sampling loop also stopped after 300 ms of wall time, so on a slow runner it could stop before the panel settled.
- **Error class:** A browser test measures a motion's duration with the wall clock. Runner load then decides the result instead of the declared motion.
- **Guard:** The test reads the end time from the panel's own transitions (`getComputedTiming().endTime`) and requires it to be at most 300 ms. It samples frames until the panel settles or has no running transitions, without a wall-clock limit. A search of the `packages/ui` browser tests found no other duration assertions that use the wall clock. There is no repository rule for this, because a duration taken from the wall clock looks the same in code as other elapsed-time values that tests use legitimately.
