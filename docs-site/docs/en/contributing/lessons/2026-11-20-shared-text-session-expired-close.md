### An expired sign-in on a shared Mail draft looked like lost access

- **What happened:** When the sign-in expired while a shared Mail draft was open, the composer turned read-only with the raw message "SESSION_EXPIRED" and offered no way to sign in again. Text that the server had not confirmed yet stayed only in the tab or on the device, and the person had no path from the composer to save it (#3851).
- **Root cause:** Cloud's application socket guard closes the socket with code 1008 and reason `SESSION_EXPIRED` when the credential expires. The shared-text provider passed every close to the application's `closeError`. Mail mapped every 1008 close to `ACCESS_DENIED`, so its `fatal()` never called `waitForSignIn()`. Notebooks read the reason and was not affected.
- **Error class:** A platform signal with one fixed meaning is left to each application to interpret, so an application that maps it differently silently loses the platform's recovery path.
- **Guard:** The shared-text provider now turns the guard's 1008 `SESSION_EXPIRED` close into `SESSION_EXPIRED` itself, before any application mapping, as it already does for 1013. `packages/cloud/src/browser/shared-text-provider.test.ts` checks this with an adapter that maps every 1008 to lost access. `mail-draft-session.behavior.test.tsx` checks that the close asks to sign in with Mail's own message, that remembered text survives sign-in and reload and is then confirmed by the server, that tab-only text keeps the page open, and that real lost access stays read-only. Mail words an expired sign-in itself, on the socket and for HTTP 401, instead of showing the transport's text.
