### Match the recovery point to the effects that can still complete

- **What happened:** The upgrade guide took its rollback backups before draining accepted work, and its pending-request recovery advice could start old software after other applications had migrated. A webhook example also promised permanent deduplication from a 24-hour receipt, and the first-Code guide activated before sharing its event place.
- **Root cause:** Recovery advice treated backups, external effects and startup as independent steps. The examples did not account for receipt expiry or activation's current event-place access check.
- **Error class:** Recovery and example guarantees outlive the state that supports them.
- **Guard:** The runbook requires one consistent database and RSQL recovery point after drain and reconciliation, names the lost changes and reconciles later external effects before old workers resume. The first-Code procedure shares the mailbox before activation. The Code SDK test compiles the published Fibel webhook with the real checker and executes it against SQLite: a fresh request after 25 hours cannot repeat a completed task, and an uncertain task outcome leaves a durable pending claim that requires reconciliation. The documentation checks and cross-provider procedure review cover the recovery instructions; no destructive restore runs in a documentation test.
