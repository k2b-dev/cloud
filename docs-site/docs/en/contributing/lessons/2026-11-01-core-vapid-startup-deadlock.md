### Core startup waited on its own VAPID transaction

- **What happened:** A fresh Core boot intermittently never reached readiness or registered its routes. Local startup tracing reproduced the wait in browser notification initialization. PostgreSQL showed the workflow retention index build waiting for the open VAPID transaction; cancelling that build let startup finish immediately.
- **Root cause:** VAPID initialization held a transaction and advisory lock while reading and writing settings through the shared pool. Bun could queue a settings read behind `CREATE INDEX CONCURRENTLY`, which was waiting for that same transaction to end. The transaction could therefore never finish. Settings now use the lock-owning transaction, both generated keys commit together, and cache invalidation follows commit. The escaped connection dates to `a22710c257`; the concurrent workflow retention index was added in `51d1da756c`. Both changes are also on `main`.
- **Error class:** Application-level database deadlock caused by escaping a transaction to its shared connection pool.
- **Guard:** `packages/cloud/src/services/notifications/browser-settings.test.ts` rejects pool-level settings calls during VAPID initialization, checks that every read and write receives the lock-owning transaction, and verifies that cache invalidation follows a successful commit and does not run after a failed key write. Repeated fresh Core boots verify the startup boundary with an empty database and NATS namespace.
