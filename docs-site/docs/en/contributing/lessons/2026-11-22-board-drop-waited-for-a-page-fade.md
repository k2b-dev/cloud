### A card dropped on the Spaces board showed in its new place only after a page-wide fade

- **What happened:** On the Spaces board, a dropped card stayed in its old column for a noticeable moment, then the whole page faded to the new picture. When the save answered, it faded again. With 50 cards on a loaded machine, the card reached its new column about 600 ms after the release, although the board updates before the save.
- **Root cause:** The board wrapped every optimistic move, every confirmed move and every rollback in `document.startViewTransition`. No card had a `view-transition-name`, so each transition was a cross-fade of the whole page. The browser first waits for a frame to capture the old picture, so the new place shows late. In the same frames, every card's overdue check and deadline label worked out "today" in the time zone again, which builds date formatters. That took about 200 ms per move.
- **Error class:** Work on the path from a release to the next frame that the interaction does not need, such as a page-wide transition or a per-row recomputation of a value that is the same for every row.
- **Guard:** `spaces-flat.browser-suite.ts` ("a dropped card lands where the line showed at once") holds the save until the card shows in its new column and counts `startViewTransition` calls during the drop, which must be zero. `todayKey` in `packages/spaces/src/presentation/deadline.ts` works out today once per minute and time zone (every zone's day starts on a whole minute). `task-overdue.test.ts` checks that 200 cards call `dates.today` once. No repository check, because a rule cannot tell which work an interaction needs.
