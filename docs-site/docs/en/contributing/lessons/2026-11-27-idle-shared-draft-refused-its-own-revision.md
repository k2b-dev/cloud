### An idle shared draft refused every update at the revision it showed

- **What happened:** `cld mail draft get` showed revision 3 of an empty shared reply draft. `cld mail draft update --revision 3` answered 409 every time, also with the lease held, while `draft discard --revision 3` succeeded. The draft occupied the conversation's reply box, so `cld mail reply` could not write either.
- **Root cause:** A revision-checked update replays the log from the cursor that was recorded with its revision base. The hourly snapshot reconciliation (`store.advance`) and saves that change nothing move an idle draft's durable cursor forward without a new revision. Pruning then removes the prefix behind the recorded cursor. The replay hit that gap, which was not tolerated because the recorded cursor lay behind the durable one, so every update became "recovery required". The prune's coverage proofs update many drafts in one transaction, which explains their identical `updatedAt`.
- **Error class:** A replay anchor that background work silently outdates. A cursor that is valid when recorded becomes unreplayable later, without any edit, and the client has no state that can succeed.
- **Guard:** `draft-document-retention.integration.test.ts` ("an idle draft takes a write at the revision it shows …") advances an idle draft like the reconciliation does, prunes past its revision base and requires the update at the shown revision without a recovery copy. A refused update and an occupied reply box now answer 409 with the current `revision` (`one-reply-draft.integration.test.ts`), and `cli.test.ts` requires that the CLI names it and that `draft create` fails when the answer names no draft.
