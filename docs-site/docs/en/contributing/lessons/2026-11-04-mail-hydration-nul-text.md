### A message with NUL bytes failed hydration on every attempt

- **What happened:** In production, one 5.4 KB `multipart/mixed` message, with 8bit inline text and a base64 attachment, failed hydration with `ERR_POSTGRES_SERVER_ERROR` on every attempt, also after a repair. Mail recorded only that code.
- **Root cause:** Hydration wrote the parsed text, the attachment names and the selected headers to Postgres as they came from the message. Postgres `text` cannot hold U+0000 (SQLSTATE 22021) and `jsonb` cannot hold `\u0000` (22P05), so the same write failed each time. A test message with NUL in its 8bit text, headers and attachment name reproduced it at the attachment name (`unnamed portal parameter $8`). Suspected: the production message carries NUL in one of these places; its exact field is not known.
- **Error class:** Text from outside the system reaches the database without the database's own limits, so data that the system cannot store fails the same write again and again.
- **Guard:** Hydration removes NUL and replaces lone surrogates (`toWellFormed`) in every text and `jsonb` value it writes: body text, HTML, parts and attachment metadata, selected headers, protocol facts and receipts. The stored source keeps the original bytes. A failed hydration now logs its SQLSTATE and the refused parameter, table or column, never the text. `message-hydration-text.integration.test.ts` loads such a message, which failed before the fix, and checks the failure log.
