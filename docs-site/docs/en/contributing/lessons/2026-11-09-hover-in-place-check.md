### A check keeps hover()'s retry scroll out of geometry tests

- **What happened:** After the bars family test moved to `hoverInPlace()` (#3013), 99 other places in 60 browser test files, with 84 hover calls, some of them in helpers, still hovered between two geometry reads of the same flow. Any of them could fail the way the bars test did, when one retry of `hover()` scrolls the page on a busy runner.
- **Root cause:** `Locator.hover()` scrolls the target into view again when it retries a failed actionability check. A test that measures viewport boxes before and after the hover then measures that scroll. The pattern was copied from test to test, because a plain `hover()` passes on every quiet run. One retry trigger is now confirmed: while a view transition runs, `elementsFromPoint()` returns only `<html>`, so the hit check fails. The Kanban drag tests hovered a card while one ran.
- **Error class:** A test compares viewport coordinates across a Playwright action that can scroll the page on its own.
- **Guard:** The `hover-in-place` check (convention TEST-16) reports each `hover()` with a geometry read before and after it in one flow, also through helpers of the same file. All such hovers now use `hoverInPlace()`. It keeps only `hover()`'s first scroll, waits out a view transition, points at a wrapped link's first line, and works in frames; a guard test in `packages/ui/test/browser.browser.test.ts` covers that. `// hover: <reason>` allows a hover whose reads do not depend on the scroll position.
