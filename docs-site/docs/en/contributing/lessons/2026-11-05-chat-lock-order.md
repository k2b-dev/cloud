### Reacting while Chat delivers a notification can deadlock

- **What happened:** A reaction immediately after a message sometimes failed with HTTP 500 and PostgreSQL `40P01`.
- **Root cause:** Reactions locked the conversation before inserting a reaction, whose foreign key needed `KEY SHARE` on the message. Notification delivery locked the message first, then inserted recipient state whose foreign key needed `KEY SHARE` on the conversation. Delivery now locks the conversation before the message, matching sends, edits, reactions, and membership changes. Its conversation lock uses `FOR NO KEY UPDATE` so an independent first push-state insert can complete its FK check instead of leaving an uncommitted row that delivery waits on.
- **Error class:** Lock-order inversion between a `FOR UPDATE` row lock and an FK `KEY SHARE` lock.
- **Guard:** `packages/chat/src/service/lock-order.integration.test.ts` holds the reaction's conversation lock, starts real notification delivery, and waits until PostgreSQL reports it blocked by that transaction. Inserting the reaction and updating its message must then complete, along with the delivery cursor and recipient aggregate. The test deterministically fails with a deadlock under the old order. A second case pauses delivery at its message lock and requires an independent first push-state insert to complete its conversation FK check.
