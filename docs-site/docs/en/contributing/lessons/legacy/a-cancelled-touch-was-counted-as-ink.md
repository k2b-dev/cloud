### A cancelled touch was counted as ink

- **What happened:** `SignatureInput in chromium > a cancelled touch is not a stroke` found one ink path instead of none in 2 of 20 local runs of the `@k2b/ui` browser files under load ([#1495](https://github.com/k2b-dev/cloud/issues/1495)). CI had not shown it.
- **Root cause:** The test's `swipe()` sent the touch over `Input.dispatchTouchEvent` and returned when the last call returned. That call returns once the browser has passed the touch on, not once the page has handled it: with the main thread blocked for 300 ms at the last move, the `touchCancel` call returned after 15 ms and `pointercancel` reached the page after the block. The count then could read the ink of the stroke still in progress. `SignatureInput` itself drops that ink in the same `pointercancel` handler and ignores later events of the cancelled pointer. A blocked main thread alone does not make the old count read 1, because Chromium dispatches the queued touch before the later read; the read gets ahead only while the touch is still on its way inside the renderer, which a loaded machine allows.
- **Error class:** State sampled before it settled.
- **Guard:** `swipe()` installs a one-shot capture listener for the last touch before it sends one, waits until the page has recorded that touch, then one frame. The cancel case first waits for the ink of the finger that is still down, then for the handled cancel, and expects no ink and no change. A case blocks the main thread for 500 ms at the last pointer event, for a lifted and a cancelled touch, and checks that `swipe()` returns only after that; the old `swipe()` returned after 205 to 220 ms.
