### A Timeline test asserted that a debounce had not fired yet

- **What happened:** The Notebooks case "Timeline returns to the scrolled rows after opening a note and Back, and after a reload" failed in Chromium in job 117943729253 of #1527, a change to Spaces only: `pendingAtSwitch` was `false` ([#1533](https://github.com/k2b-dev/cloud/issues/1533)).
- **Root cause:** The test scrolled the Timeline, waited one animation frame and one task on the real clock, and then asserted that the 150 ms scroll-pause save had not run yet. On a slow runner the frame took longer than the pause. A 300 ms block of the main thread in that frame, or a 20× CPU throttle through the Chromium DevTools protocol, failed the test in every run. The product was correct: a display switch runs the Timeline cleanup, and the cleanup writes an unsaved position before the next display mounts.
- **Error class:** Fixed wait instead of a condition.
- **Guard:** The test sets the scroll position and switches the display in the same task, so no scroll event or save can come between them. It asserts only that the Timeline comes back at the new position, and it fails in Chromium and WebKit when the cleanup does not write the position. The `test-waits` check cannot find this pattern: a frame wait has no duration to judge, tests call `requestAnimationFrame` about 160 times for other reasons, and only the product's timing tells whether a later read expects a delayed effect to be absent. The convention is in [Wait for conditions, not time](/en/docs/contributing/testing#wait-for-conditions-not-time).
