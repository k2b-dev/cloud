### Pulse metrics bypass the outbound address policy

- **What happened:** Pulse metrics sources could reach internal endpoints without an operator exception.
- **Root cause:** The metrics scraper called `fetch()` on the source endpoint without the platform guard.
- **Error class:** Server-side request forgery.
- **Guard:** Pulse validates and pins each request and redirect through `resolveAllowedNetworkAddresses` and `pinnedNetworkLookup`. Only Cloud admins can release internal Pulse targets per base; save-time checks, every scrape and every redirect use the current entries and effective port. Other applications retain their operator env registries. Administrator-chosen health webhooks, Geo, Assistant rsql, outgoing SMTP and bounce IMAP are guarded too. Their HTTP paths use `createAllowedNetworkFetch`, which never follows redirects. SMTP connects to checked IP literals; IMAP uses a pinned lookup containing every checked address. Both preserve the original TLS `servername`. The `network-guard` check rejects global `fetch()` in guarded server roots and endpoint files, reports missing covered paths, and requires mail constructors to import the guard or outgoing-mail resolver. Loopback and injected-lookup tests cover blocked and operator-allowed targets, DNS rebinding, cancellation and streaming. SDK clients that resolve their own hosts cannot be pinned: use them only to sign locally, then send through a pinned transport. Platform and Pulse tests cover allowlist parsing, all DNS answers, blocked targets, redirect credentials, byte limits, and the total deadline.
