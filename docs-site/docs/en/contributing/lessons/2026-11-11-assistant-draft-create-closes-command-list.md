### The Assistant's first draft save still closed the "/" list

- **What happened:** In WebKit, `catalog and resource recovery in real fullview at 1440px` in `packages/chat/src/frontend/ChatPanel.browser.test.ts` failed again and again (#2233). The retry row "Commands from apps could not be loaded" was detached before the click. The field still held `/notes` and kept focus, but no list was open. The trace had no blur and no key, only "command list gone" about 2 s after typing. By then the URL had `?conversation=…`.
- **Root cause:** A new chat's draft saves itself 2 s after the last edit and creates the chat first. That create changed the composer's `draftKey` from `__new__` to the chat ID. The controller made the chat active before the Assistant had moved its draft there, so for one update the field showed the new chat with no draft. `ChatComposer` also read `props.draftKey` directly in its effects. Every new key, and every recomputation that returned the same key, reset the draft's state and closed the list. A fast runner clicked the retry row before the save, a slow one after it. A person who pauses in the list for 2 s sees the list close.
- **Error class:** The identity of a draft changes when only its storage location changes. Also, a keyed reset that runs when its key is recomputed, not only when its value changes.
- **Guard:** `ChatComposer` keys its resets on a memo of `draftKey`, so only a new value resets them. `createConversation` takes `beforeOpen`, which runs in the same update that makes the chat active. The Assistant moves the new draft there and keeps its draft identity when the draft's own save creates the chat. A send or an app command still gets a new key and keeps its `follow()` path. The fullview recovery test now waits for that create and checks that the list never closed. On the old code it fails every time, at every runner speed.
