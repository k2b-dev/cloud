### Idle applications start background consumers without work

- **What happened:** Every Grids process started 32 workflow record-event pull loops even without an enabled record-event workflow. Every application process also ran a scheduler worker for the same hourly links cleanup.
- **Root cause:** Record-event reconciliation started the partition worker unconditionally, and shared links provisioning also registered retention in every application. Stopping readers alone would leave idle record writes accumulating in the workflow queue.
- **Error class:** Background consumers follow process lifetime instead of domain demand or the owning service.
- **Guard:** `workflow-record-events.test.ts` counts zero queue starts across three concurrent idle reconciliations. `record-events.integration.test.ts` checks zero idle workers, exactly 32 durable consumers with one worker after activation, zero workers after disabling, ordered delivery across restart, one worker start under concurrent reconciliation, and zero workflow lookups for 1,000 historical messages while recent publications and the activation boundary still reach dispatch. `record-event-outbox.integration.test.ts` verifies zero publications without workflow demand, retained feed rows and snapshots, immediate eligibility after a concurrent activation commits, and no demand from trashed bases, and one runtime hint per base trash/restore action. A unit guard coalesces 1,000 hints during a blocked refresh into one pending refresh. `links/runtime.integration.test.ts` counts zero retention schedulers in a non-Core application and one per Core replica; `define-app.startup.test.ts` verifies the declared app ID reaches links startup.
